# myPDM 系统用户权限说明

> **事实源**：权限定义的唯一权威来源为 `permissions/permissions.json`，本文档为其人类可读镜像。
> **代码生成**：`python tools/gen_permissions.py` → 后端 `backend/app/permissions/_generated.py` / 前端 `frontend/src/constants/permissions.generated.ts`（`npm run build` 的 prebuild 钩子自动执行）。
> **适用代码版本**：v3.1.3（「Master → Revision → Iteration」三层数据模型）。
> **最后更新**：2026-08-01

## 一、权限体系总览

### 1.1 两层判定：角色门 + 对象策略

```
请求 → OAuth2 Bearer → get_current_user（解 JWT、查用户）
     → get_current_active_user（status == "active"）
     → require_permission("perm:action")        ← 第一层：角色门（查 PERMISSIONS 矩阵）
     → enforce_object_policy("policy_name", …)  ← 第二层：对象策略（路由内手工调用）
```

- **第一层（角色门）**：`require_permission(perm)` 依赖注入，只看 `user.role ∈ PERMISSIONS[perm]`。启动时对未定义权限名 fail-fast（`KeyError`）。
- **第二层（对象策略）**：判定"这个具体对象你能不能动"（创建者 / 审批人 / 保管人 / 单据参与者 / 项目经理 / 文件夹所有者 / 用户组成员）。

> ⚠️ **重要机制约束**：`permissions.json` 中的 `object_policy` 字段只会生成一份**声明式清单** `OBJECT_POLICIES`（`_generated.py`），`require_permission()` **不会自动执行它**（见 `backend/app/permissions/__init__.py:22-32`）。策略是否真正生效，取决于路由函数里有没有手工调用 `enforce_object_policy(...)`。
>
> 为防止"声明了却没人调用"长期潜伏，已加静态防回归测试
> `backend/tests/test_permission_wiring.py`：每条声明的策略都必须能在
> `backend/app/` 下找到对应的 `enforce/check_object_policy` 调用，否则测试失败。

### 1.2 角色定义

| 角色 | 标识 | 定位 |
|---|---|---|
| 管理员 | `admin` | 全部权限；用户/用户组管理、系统设置、自定义字段定义、操作日志、软删除清理、强制签入 |
| 工程师 | `engineer` | 核心业务读写：零部件/图文档/构型/BOM/变更/库存/项目；可删除关联、附件与 BOM 行，不可删除主对象 |
| 生产人员 | `production` | 查询、下载、导出；可参与库存单据全流程与项目任务；可查看零部件附件 |
| 访客 | `guest` | 只读；不可导出、不可评论、不可进入 BOM 工具、3D 预览、压缩包浏览、用户管理 |

**独立于系统角色的第二套角色**：项目模块内另有「**经理 / 成员**」（`project_members.role_in_project`），两者叠加生效，详见 3.9。

### 1.3 三层数据模型对权限的影响

零部件、图文档、构型项均为 `Master → Revision → Iteration` 三层结构，这直接决定了权限的作用位置：

| 层 | 权限相关字段 | 说明 |
|---|---|---|
| Master | — | 稳定身份（编号/名称）。删除 Master 需 `*:delete`（仅 admin）。图文档的**用户组关联挂在此层** |
| **Revision** | `check_out_user_id`、`status` | **权限判定的主战场**：几乎所有端点以 `revision_id` 为路径参数；签出锁在此层 |
| Iteration | `creator_id` | 「谁做了这次修改」记在迭代上（v3.1.3 起从 Master/Revision 下移） |

**签出锁 = 一条隐式对象策略**：签入 / 撤销签出 / 编辑内容一律要求 `check_out_user_id == 当前用户`，由各模块 CRUD 内联判定（`crud_parts.py:468`、`:500`；`routers/documents.py:266`；`routers/configuration.py:362` 等）。仅 `*:force_checkin`（admin）可越过。

**`creator_id` 的正确读法**：凡涉及"创建者"的权限判定，都必须**回溯迭代层**，不能读
Master/Revision 上的同名属性（那里没有这一列，`getattr` 恒为 `None`，会静默失效）。
图文档侧的统一入口是 `crud_groups.get_document_creator_id()`。

## 三、各模块权限行为（矩阵之外的规则）

### 3.1 零部件（`/api/parts`，`routers/parts.py`）

- 列表 / 详情 / 版本 / 迭代查询：`parts:read`（全角色）。
- 生命周期端点各有独立权限：`checkout` / `checkin` / `undocheckout` / `upgrade` / `release` / `freeze` / `obsolete` / `cascade_*`（admin+engineer），`force_checkin` / `unfreeze` 仅 admin。
- 状态前置条件由 CRUD 强制：仅 `draft` 可签出；被签出的版本不可发布；只有签出者本人可签入 / 撤销签出。
- BOM 端点复用 BOM 权限：读 `bom:tree`（排除 guest），增改 `bom:create_relation`，删 `bom:delete_relation`（admin+engineer）。
- 附件端点：列表与文件读取全角色（`attachments:list` / `attachments:download`），上传 `attachments:upload`、删除 `attachments:delete`（均 admin+engineer）。删除时校验「附件 → 迭代 → 版本」归属，并写操作日志。
- CAD 工作台：`POST /cad/bom-match` 用 `parts:read`，`POST /revisions/{id}/cad/bom-sync` 用 `parts:update`。

### 3.2 图文档（`/api/documents`）+ 用户组内容访问

除角色门外，图文档**附件内容**受用户组约束（`document_content_access` 策略，`crud_groups.py`）：

| 条件 | 结果 |
|---|---|
| 用户为 admin | 允许 |
| 文档创建者本人（回溯最早迭代的 `creator_id`） | 允许 |
| 文档未关联任何用户组 | 允许（留空 = 全员可访问） |
| 用户所属组 ∩ 文档关联组 ≠ ∅ | 允许（多组为「或」关系） |
| 其他 | 403 |

- 生效范围：附件列表 / 下载 / 预览 / 3D / 压缩包浏览（`documents.py`、`attachments_v2.py` 各处）。
- **不隐藏文档元数据**：列表接口对每行返回 `group_ids` 与 `accessible` 标记（由
  `crud_groups.annotate_documents_access()` 批量补齐：用户组 1 次查询 + 组关联 1 次查询，
  仅对"会被拒绝"的行才回溯创建者），前端据此置灰 + 🔒 + 提供「可查看」筛选。
- 关联关系挂在 **Master** 上（`document_group_links.document_id → document_masters.id`），对全部版本与迭代统一生效。
- 组关联的写入点：新建文档时 `group_ids`；修改需先签出且为签出者本人。
- 用户组本身：`user_groups:read`（admin/engineer/production）、`user_groups:manage`（仅 admin）。删除用户组会级联删除 `DocumentGroupLink`，**原先仅关联该组的文档退化为全员可访问**。

### 3.3 附件 V2（`/api/v2/attachments`）与媒体令牌

浏览器需直连的操作（预览 / 原生下载 / glTF / 压缩包）使用**短寿命媒体令牌**，不把会话 JWT 放进 URL：

1. 前端先调 `GET /{id}/media-token?action=<action>`（`get_current_active_user` + 内联 `has_permission(_ACTION_PERM[action])` + 用户组访问校验）；
2. 拿到令牌后拼到目标 URL 的 `?token=`；
3. 目标端点只做 `verify_media_token(token, attachment_id, action)`，不再校验角色。

令牌 TTL 300 秒，载荷绑定 `aid` + `act` + `typ=media`，跨附件 / 跨动作复用会 403。

`action → 权限`：`preview`/`office-pdf` → `attachments:preview`；`direct-download` → `attachments:direct_download`；`gltf` → `attachments:gltf`；`archive-tree`/`extract-file` → `attachments:archive_browse`。

### 3.4 BOM（`/api/bom`）

`bom:*` 全部**排除 guest**。`bom:create_relation` 与 `bom:delete_relation` 均为 admin+engineer（增删对称）。

### 3.5 构型项与配置方案（`/api/configurations`）

- 构型项：读全角色；增删改与 `configuration.item:manage` / `configuration.doc:manage` 为 admin+engineer；`delete` 与 `force_checkin` 仅 admin；有完整签入签出链。
- 配置方案流程：`submit` / `withdraw` / `archive` 用 `profile:activate_archive`；`status` 直改用 `profile:change_status`（仅 admin）；`reopen` 用 `profile:update`。
- **审批**：`POST /profiles/{id}/review` 用 `profile:approve`（admin/engineer/production，排除 guest）+ 对象策略 `profile_approver_or_admin`；`crud_configuration.review_profile` 内的审批人校验保留作纵深防御。
- **抄送**：`POST|DELETE /profiles/{id}/cc` 用 `profile:cc_manage`（全角色，与 `ecr:cc_manage` 对齐）。

### 3.6 变更管理 ECR / ECO

- 读类（列表、详情、状态日志、BOM 追溯、抄送）全角色；写类 admin+engineer。
- 对象策略：ECR 的 update/delete/submit/withdraw → `ecr_owner_or_admin`，review → `ecr_approver_or_admin`；ECO 的 update/delete/submit/withdraw → `eco_owner_or_admin`。
- ECO 的 `review` 端点挂 `eco:update` + owner 策略（不是"审批人"策略）。
- PDF 导出由**前端生成**（`services/ecPdfExport.ts`），后端无对应端点。

### 3.7 库存（`/api/inventory`）

- 仓库 / 物料：读全角色，写 admin+engineer，删仅 admin。
- 单据：读全角色，`write` / `delete` / `submit_withdraw_approve` 含 production。
- **单据级门禁 `inventory_doc_participant_or_admin`**：admin / 创建者 / 保管人 / 指定审批人。
  由 `routers/inventory.py` 的 `_enforce_doc_participant()` 在 8 个单据端点统一调用
  （`GET/PUT/DELETE /documents/{id}`、`submit`、`withdraw`、`review`、`assign-keeper`、`cancel`），
  与 `crud_inventory.list_documents` 的行级可见性**同口径** —— 列表里看不到的单据，
  拿到 UUID 也读不动。
- 过账 `post` 用更严的 `inventory_keeper_or_admin`（仅保管人或 admin）。
- 状态守卫：仅 `draft` 可编辑，仅 `draft`/`rejected` 可删除，仅 `reviewing` 可审批。

### 3.8 用户看板（`/api/dashboard`）

- 全部看板权限对四种角色开放，靠所有权 / 共享权限约束。
- **判定唯一入口**：`_check_folder_edit_permission(folder, user, db)` —— 算出「看板所有者」+
  「本文件夹 ∪ 全部祖先上被授予 edit 的用户集合」，再交给 `dashboard_folder_editor` 策略。
  文件夹改名 / 删除 / item 增删 / 共享管理全部走这一个入口，口径一致。
- 策略只接受显式关键字参数（`owner_user_id=` / `editor_user_ids=`），不从对象属性推断
  （`DashboardFolder` 既无 owner 列，也无法表达祖先继承）。
- 共享管理类端点另有更严的「仅看板所有者」前置检查。
- 根文件夹删除额外要求 admin；看板全量导入导出仅 admin。

### 3.9 项目管理（`/api/projects`）—— 双层角色

| 项目角色 | 来源 | 能做什么 |
|---|---|---|
| 经理 | `role_in_project == "经理"`，或项目 owner，或系统 admin | 编辑/删除项目、成员管理、任务增删改与移动排序、依赖与自动排期、更新任意任务状态、删除任何评论 |
| 成员 | `role_in_project == "成员"` | 查看项目/任务/甘特/交付物、任务关联对象增删、发表评论（仅删本人）、**仅更新自己负责的任务状态** |

- 管理者集合 = `{owner} ∪ {经理成员}`（`projects.py:41-47`），交给 `project_manager_or_admin` 策略的 `manager_ids` 参数。
- 非管理者但为成员的操作走 `_require_member`；非成员且非 admin 一律 403「非项目成员」。
- 项目可见性：`list_projects` 对非 admin 只返回自己参与的项目。
- owner 恒为经理，角色不可下调、不可移除；移除成员会清空其名下任务负责人。
- 靠路由内联判定的三项：`project.task:update_status`（经理或任务负责人）、`project.task:link`、`project.task:comment`（成员即可；删评论时非经理仅限本人）。
- **前端已按项目角色渲染**：`GET /projects/{id}` 返回 `is_manager` 与 `my_role_in_project`，
  `Projects.tsx` 的 `isManager = can('project.task:create') && currentProject.is_manager`，
  「成员」不再看到管理类按钮。
- 系统角色与项目角色**叠加生效**：`production` 即使是项目经理也无 `project:update` /
  `project.member:manage`（这两项只给 admin+engineer）；`guest` 可读项目但不可评论。

### 3.10 通知中心（`/api/notifications`）

读用 `notifications:read`，写（标记已读 / 全部已读 / 清除已读）用 `notifications:manage_own`，两者均全角色开放；所有操作以 `current_user.id` 为作用域，只能读写自己的通知。

### 3.11 AI 助手（`/api/assistant`）

`assistant:chat` / `assistant:download_artifact` 全角色开放。**不构成权限绕过**：助手调用业务接口时通过进程内 ASGI 转发并**携带调用者本人的 token**（`assistant/api_gateway.py:74-96`），权限在真实端点重判；另有只读白名单 `is_allowed(path)` 与按角色过滤的接口目录。

### 3.12 用户 / 用户组 / 日志 / 自定义字段 / 数据管理 / 同步

- `users:read`（列表）对全角色开放 —— 看板共享选人、任务指派、审批人/保管人选择都依赖它；
  但**手机号仅 admin 与本人可见**（`routers/users.py` 对非 admin 置 `phone = None`）。
  `users:read_detail` 及所有写操作仅 admin。管理员通过 `PUT /users/{id}` 传 `password`
  即为重置密码，并置 `must_change_password = true`。
- 用户导入导出为纯前端实现（数据源为 `users:read`），UI 上以 `isAdmin()` 限制。
- 自定义字段：定义的读全角色，定义的写 / 排序 / 重置仅 admin；字段值的写为 admin+engineer。
- 操作日志 `logs:read`、软删除统计与清理 `admin.soft_delete:*`：仅 admin。
- 数据同步只有 `GET /api/sync/status`（`sync:read`，全角色）。
- 系统配置 `GET /api/settings/cad-naming` 挂 `parts:read`（需登录）。

## 六、注意事项

1. **前端权限只是 UI 控制**：隐藏按钮 ≠ 接口保护，所有写操作必须有后端门禁。
2. **两层判定都要写**：新增带 `object_policy` 的权限时，必须在路由里手工调用
   `enforce_object_policy`。`test_permission_wiring.py` 会拦住漏调用。
3. **策略入参必须显式传递**：不要依赖 ORM 对象属性（模型字段搬迁会让 `getattr` 静默返回 None）。
4. **测试请用真实 ORM 对象 / conftest 工厂**：`SimpleNamespace` 会掩盖模型字段变更导致的策略失效。
5. **用户状态**：`status != "active"` 的用户即使角色正确也无法通过 `get_current_active_user`。
6. **强制改密**：管理员替他人改密码后 `must_change_password = true`，该用户下次登录被引导到 `ForcePasswordChange`。
7. **权限变更流程**：改 `permissions/permissions.json` → `python tools/gen_permissions.py`
   （或 `cd frontend; npm run build` 自动触发）→ 前后端常量同步更新。
   切勿手改 `_generated.py` / `permissions.generated.ts`（`test_generated_matches_permissions_json` 会拦）。
8. **图文档用户组**：仅约束附件内容，不隐藏元数据；删除用户组会让原文档退化为全员可访问。
