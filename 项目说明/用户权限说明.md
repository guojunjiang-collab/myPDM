# Amo 系统用户权限说明

> **事实源**: 权限定义的唯一权威来源为 `permissions/permissions.json`，本文档为其人类可读镜像。  
> **代码生成**: `python tools/gen_permissions.py` → 后端 `_generated.py` / 前端 `permissions.generated.ts`。  
> **版本**: v1.3 — 权限系统巩固（Phase 0–5，详见 `docs/superpowers/plans/2026-06-17-permission-system-hardening.md`）。

## 角色定义

系统共有 4 种用户角色：

| 角色   | 英文标识         | 说明                                      |
| ---- | ------------ | --------------------------------------- |
| 管理员  | `admin`      | 系统最高权限，可管理所有数据和用户                       |
| 工程师  | `engineer`   | 核心业务操作权限，可创建和编辑零件/部件/图文档/变更单/库存，可删除关联图文档和附件    |
| 生产人员 | `production` | 可查看所有业务数据，可下载/预览附件、导出 Excel/BOM，不可编辑/删除 |
| 访客   | `guest`      | 可查看数据和下载/预览附件，不可导出、编辑、删除                |

### 权限方法定义

```typescript
// frontend/src/stores/auth.ts
function can('perm:action') → 根据权限矩阵判定当前用户角色是否在允许列表中
function canEdit()          → can('parts:create')                    // 新增/编辑/关联
function canDownload()      → can('parts:export')                    // 导出/下载
function canPreview()       → true                                    // 预览（所有角色）
function isAdmin()          → can('parts:delete')                    // 删除主体/管理用户
```

> 权限判定统一由 `can()` 完成，底层读取 `permissions/permissions.json` 生成的权限矩阵。旧版 `canEdit`/`canDownload`/`isAdmin` 保留为 `can()` 的薄封装，新代码可直接使用 `can('permission:name')`。

## 后端 API 权限控制

### 权限检查机制

所有需要认证的 API 通过 `require_permission()` 依赖注入进行权限检查（定义于 `backend/app/permissions/__init__.py`），权限定义来源为 `permissions/permissions.json`：

```python
from ..permissions import require_permission, has_permission, enforce_object_policy

# 角色门（替代旧 require_role）
current_user: User = Depends(require_permission("parts:read"))

# 内联权限判定
if not has_permission(current_user, "parts:delete"):
    raise HTTPException(status_code=403, detail="权限不足")

# 对象级策略（创建者/审批人/保管人等）
enforce_object_policy("ecr_owner_or_admin", current_user, ecr)
```

认证链：`OAuth2PasswordBearer` → `get_current_user`（解码JWT+查用户） → `get_current_active_user`（检查status=="active"） → `require_permission("perm:action")`（查生成矩阵）

### 使用方式

```python
# 仅管理员
current_user: User = Depends(require_permission("parts:delete"))

# 管理员 + 工程师
current_user: User = Depends(require_permission("parts:create"))

# 管理员 + 工程师 + 生产人员
current_user: User = Depends(require_permission("parts:export"))

# 所有角色
current_user: User = Depends(require_permission("parts:read"))
```

### 对象级策略

除角色门之外，以下端点额外执行对象级策略（`enforce_object_policy`）：

| 策略名 | 规则 | 应用端点 |
| - | - | - |
| `ecr_owner_or_admin` | 仅创建者或 admin | ECR 编辑/删除/提交/撤回 |
| `ecr_approver_or_admin` | 仅指定审批人或 admin | ECR 审批 |
| `eco_owner_or_admin` | 仅创建者或 admin | ECO 编辑/删除/提交/撤回 |
| `inventory_keeper_or_admin` | 仅指定保管人或 admin | 库存单据过账 |
| `dashboard_folder_editor` | 文件夹所有者，或被分享且权限为 edit | 看板文件夹增删改、分享管理 |

### 附件预览端点（媒体令牌）

以下端点使用短寿命**媒体令牌**（5 分钟，作用域绑定 attachment_id + action），不再将会话 JWT 放入 URL：

| 端点 | 所需权限（签发时校验） | 说明 |
|------|---------|------|
| `GET /api/v2/attachments/{id}/media-token?action=preview` | `attachments:preview` | 签发预览令牌 |
| `GET /api/v2/attachments/{id}/media-token?action=direct-download` | `attachments:direct_download` | 签发原生下载令牌 |
| `GET /api/v2/attachments/{id}/media-token?action=gltf` | `attachments:gltf` | 签发 3D 预览令牌 |
| `GET /api/v2/attachments/{id}/media-token?action=archive-tree` | `attachments:archive_browse` | 签发压缩包浏览令牌 |
| `GET /api/v2/attachments/{id}/media-token?action=extract-file` | `attachments:archive_browse` | 签发文件提取令牌 |

前端在打开预览/下载/3D 前先调用 `mediaApi.token(id, action)` 获取媒体令牌，再拼入 URL `?token=<media_token>`。

## 注意事项

1. **前端权限仅为 UI 控制**：隐藏按钮不等于接口保护，所有写操作必须经过后端权限校验
2. **production 角色**：可查看数据、下载/预览附件、导出数据、管理库存单据，但不能创建/编辑/删除业务实体
3. **guest 角色**：可查看数据、下载/预览附件，不能导出、创建、编辑、删除，不能查看管理工具、BOM树、STP 3D预览
4. **engineer 角色**：可创建/编辑数据，可删除关联图文档和附件，不能删除零件/部件/图文档主体和构型/配置方案
5. **用户状态**：被禁用的用户（`status != "active"`）即使角色正确也无法操作
6. **权限事实源**：所有权限配置集中在 `permissions/permissions.json`，通过 `python tools/gen_permissions.py` 生成后端和前端常量，自动保持前后端一致
7. **变更管理特殊性**：ECR/ECO 除了角色检查，还有创建者/审批人等业务级权限控制（创建者可编辑自己的草稿，指定审批人可审批）
8. **库存模块特殊性**：仓库/物料仅 admin+engineer 可写，库存单据允许 production 参与管理（增删改审批），过账需为指定保管人或 admin
9. **附件预览安全**：PDF 预览、文件下载、3D 预览等使用独立短寿命令牌（5 分钟），不再将登录令牌放入 URL，防止泄漏
